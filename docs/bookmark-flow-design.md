# 栞の流れAPI 設計書（Issue #12）

状態: 実装前の設計。

関連: [Issue #12](https://github.com/Megane14916/book-bear/issues/12) / 基準: main `6f716d4`（PR #21マージ後） / 2026-11-03（日本時間）

## 1. 目的・範囲

指定ユーザーが指定書籍につけた栞を、ページ番号ではなく投稿した古い順にたどれるようにする。対象は `GET /api/v1/users/{userId}/books/{bookId}/bookmarks` の1操作。栞CRUD・本人一覧はIssue #11の実装を維持し、フィード・SNS操作・UIは含めない。

パラメーター・応答の詳細は [API設計書](api.md#23-栞栞の流れ)、[既存Zodスキーマ](../apps/api/src/modules/bookmarks/schemas.ts)、並びと参照関係は [DB設計書の6.1「栞の流れ」](database.md) を参照する。新しいパス・応答形式は作らない。

## 2. 振る舞いと認可

JWTは任意。提示された場合は既存の `authentication.optional` で必ず検証し、不正・期限切れなら401。本人かどうかは検証済みJWTのsubとパスのuserIdの一致で判断し、匿名・正式による閲覧権限の差は設けない。metadataやクライアント指定の匿名状態は信用しない。

| 対象・閲覧者 | 返す内容 |
|---|---|
| 対象プロフィールまたは書籍が存在しない | 404 `NOT_FOUND` |
| 本人（匿名・正式とも） | 対象の本に属する本人の公開・非公開の未削除栞 |
| 未認証または他のユーザー | 対象ユーザー・本の公開中かつ未削除の栞だけ |
| ユーザーと本は存在するが、本棚の組み合わせ・閲覧可能な栞がない | 200。公開ヘッダーと `items=[]`、`nextCursor=null` |

- 非公開栞しかない本棚と、組み合わせがない本棚は第三者へ同じ空結果を返す。本棚の存在、userBookId、読書状態・進捗、非公開栞の本文・件数は公開しない。削除済み栞は本人にも返さない。
- ヘッダーのauthorは既存の `UserSummary`、bookは `BookSummary`。公開プロフィール要約と共有書籍情報だけを使い、レスポンス直下へ各1回置く。itemsは `BookmarkFlowItem` とし、author・bookを繰り返さない。
- 本文とネタバレ表示の責務は [APIの共通ルール](api.md#1-共通ルール) に従う。isSpoilerや表示設定でAPIの閲覧権限・並び順を変えない。
- 成功・失敗とも `Cache-Control: no-store`。既存のJWT検証、Data API不使用、アプリ専用DBロール、Hyperdriveのキャッシュ無効を維持する。

## 3. 処理の流れ

1. 任意JWTを検証し、既存の `BookmarkFlowParams`／ページング入力でUUID・limitを検証する。カーソルもDB取得前に解析する。
2. 対象プロフィールと書籍の公開ヘッダーを取得する。存在しなければ404。本人判定とヘッダー取得に、プロフィール件数集計等の不要な処理は持ち込まない。
3. `user_books(user_id, book_id)` の既存UNIQUEを使い、対象のuserBookIdを特定する。なければ空結果を返す。ブラウザへ本棚のレコードは返さない。
4. 栞のSQLに対象userBookIdと `deleted_at IS NULL` を必ず含め、本人以外は `visibility='public'` を加える。これらの条件を適用してから、昇順の境界・並び順・limit+1件で絞る。非公開・削除済みの行を取得後に除外する方式は採らない。
5. 返却する最大limit件について、Issue #11の `withCounts` を同じbookmarksモジュール内で再利用し、いいね・未削除返信を対象ID集合でそれぞれ一括集計する。関数は `T extends { id: string }` の栞データを受け取り、入力型を保ったまま集計フィールドを追加する。既存のカードと今回の軽量な `BookmarkFlowItem` に共用し、集計のためにauthor・bookを取得しない。likedByMeは検証済み閲覧者のUIDを使い、未認証ならfalse。空結果では集計を実行しない。
6. ヘッダー・軽量なitems・nextCursorを既存の `BookmarkFlowPage` で返す。itemsのSQL射影には栞の公開項目だけを指定し、author・bookや私有項目を混入させない。

処理は読み取りのみで、行ロック・明示トランザクション・外部書籍API呼び出しは追加しない。既存withDatabaseの短いDB処理範囲で完結させ、投稿数に比例するDB往復を作らない。いいねと返信の直接多重JOINによる件数の水増しも避ける。

## 4. 昇順カーソル

- `ORDER BY bookmarks.created_at ASC, bookmarks.id ASC`。ページ番号・updatedAt・本棚への登録日時は順序に使わず、編集でもcreatedAtは変えない。
- 既定15・最大30件。SQLではlimit+1件を取得し、返却件数を超える閲覧可能な行があるときだけ、最終返却行の日時・IDからnextCursorを生成する。非公開行だけを理由に次カーソルを返さない。
- [既存カーソル処理](../apps/api/src/shared/cursor.ts) のBase64URL形式・解析・高精度日時を再利用する。次ページの比較は **`(created_at, id) > (lastCreatedAt, lastId)`** とし、既存の降順用 `olderThan` の動作は変えない。必要な昇順比較だけを追加する。
- 境界日時はPostgreSQLからUTC・小数6桁の文字列で取得し、SQLのtimestamptz比較へそのまま渡す。JavaScript Dateを経由したミリ秒への切り捨てを避け、同一日時はIDで安定させる。
- 署名・有効期限・対象UIDの埋め込み・追加Secretは導入しない。有効な別ユーザー・別書籍・別一覧のカーソルも境界値にすぎず、SQLの対象・公開条件を毎回適用する。不正形式・日時・UUIDは400 `INVALID_CURSOR`、空文字は既存入力スキーマの400 `VALIDATION_ERROR`。
- 境界行が論理削除されても続きは取得できる。ページ間で非公開化・削除された行は次回取得時に除外する。これは固定スナップショットではなく、公開範囲・データ変更時に結果が変わることを許容する。

## 5. 設計判断・契約への影響

| 判断 | 理由・比較 |
|---|---|
| 既存bookmarksのroutes/http/serviceを拡張 | CRUDと同じ認証・集計・スキーマを利用できる。新しいRepository基盤や汎用ページング機構は作らない |
| 組み合わせなし・公開栞なしは空結果 | 既存契約を守り、第三者へ私有本棚の有無を明かさない。ヘッダー対象自体の不存在とは区別する |
| SQLで公開条件を付けてから件数制限 | 非公開本文や件数の漏えいを防ぎ、ページサイズとnextCursorも閲覧可能な栞だけで判定できる |
| 既存カーソルと集計を再利用 | OFFSETによる位置ずれ・日時精度の欠落・N+1を避ける。今回不要な署名管理・キャッシュ・固定スナップショットは追加しない |

共通エラーの形式・認証障害・内部エラーの扱いは [API設計書](api.md#共通エラーレスポンス) に従う。500/503時もSQL・接続情報・トークンを公開しない。本操作に書き込みや正式登録限定の条件はなく、匿名であることを理由に403を返さない。

対象1操作をplannedRoutesから実ルートへ移し、同じoperationId・パス・JSON形状・既定値を維持する。実装状態・説明・必要な認証エラーを実挙動へ合わせ、[既存の契約検証](../apps/api/src/contracts/openapi.test.ts) と生成型チェックを残す。全36操作の一意性を維持し、未実装件数は14→13へ更新する。生成物は既存手順で再生成し、手編集しない。MSWは未導入のため新規モック基盤を作らない。

## 6. 検証方針と将来の注意点

署名済みJWT・使い捨てDB・アプリ専用ロールを使い、HTTP応答と実DBの条件を確認する。実装完了時の型・契約・テスト・ビルド確認は [開発ルール](development.md) に従う。

| 項目 | 必須確認 |
|---|---|
| 認証・認可 | 未認証・本人の匿名／正式JWT・別人の匿名／正式JWTを比較。不正・期限切れJWTは401でDB前に拒否。metadata偽装やuserId／bookId変更でも他人の非公開栞を返さない |
| 空・不存在・削除 | プロフィール／書籍不存在404、組み合わせなし・栞なし・削除済みのみは空結果。非公開のみは本人へ返し、第三者には空結果。本人でも削除済みは返さない。ヘッダーと私有項目の非露出を確認 |
| 並び・境界 | ページ番号逆順・null、同一日時・マイクロ秒差、15件境界・上限30・最終ページ、複数ページで重複／欠落なし。編集で順序不変、境界行削除・途中追加後も正しい境界で継続 |
| カーソル・公開変更 | 不正形式・日時・UUID・空文字・limit不正は400。別ユーザー／本／降順一覧のカーソルでも認可維持。ページ間の非公開化・削除を再評価し、隠れた栞だけでnextCursorを作らない |
| 集計・応答・障害 | 複数いいね／返信の実数、削除返信除外、likedByMe、1件と15件でDB往復が増えないこと、Zod応答適合、itemsのauthor／book重複なし、no-store、DB障害の安全なエラー |
| 既存機能 | CRUD・本人一覧・公開本一覧・認証・生成契約の回帰なし。実Workersの署名検証とDB接続も確認。CI共有DBのfixtureを独立させる |

既存の `idx_bookmarks_flow(user_book_id, created_at, id)` と本棚UNIQUEを使う方針とし、DB列・制約・新規インデックス・マイグレーション・依存ライブラリは追加しない。公開栞が少ない大きな本棚等で遅くなった場合に、実データに近い分布と `EXPLAIN ANALYZE` で検証し、公開栞向け部分インデックス等を検討する。レート制限や汎用基盤の追加は今回の実装範囲に含めない。
