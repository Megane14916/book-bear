# 開発・推薦評価用ダミーデータとseed基盤 設計書

対象は [Issue #33](https://github.com/Megane14916/book-bear/issues/33)。固定データでフロントエンドの主要画面を確認し、[Issue #30](https://github.com/Megane14916/book-bear/issues/30) で推薦方式を同じ条件で比較できるようにする。#33を先行し、両Issueの実装を `feat/semantic-book-recommendations` にまとめて1つのPRでレビューする。

## 1. 機能設計

### データセットと業務ルール

- Gitで版管理するJSONに、ユーザー・プロフィール10〜20人、書籍30〜50冊、栞150〜300件を目安に収録する。本棚・いいね・フォロー・返信は検証に必要な件数を用意する。件数は目安とし、ケースの質を優先する。
- 人物の心理・成長、謎解き、SFの世界観、技術・実用知識、文学的表現など、嗜好の違いが日本語の栞に現れるようにする。同じ本を異なる視点で語る例と、似た嗜好のユーザーが異なる本を読む例を入れる。評価対象ユーザー、上位候補として期待する書籍や傾向、第三者の非公開栞にしか根拠がないケースをデータの論理キーで別途記録する。
- 公開／非公開、ネタバレ有無、ページ番号あり／なし、長文／短文、投稿が多い／少ないユーザー、いいね・返信あり、書影なし、本棚の3状態（`want_to_read` / `reading` / `completed`）、本棚や栞が空のユーザーを含める。架空の書籍はダミーと分かる表記を付け、ISBNなしの手動登録相当とする。実在書籍の展開やページ番号は確認できる情報に限る。
- 本棚はユーザーと書籍の組で一意とし、栞はその本棚を参照する。匿名ユーザーの栞は非公開とする。いいね・返信は正式ユーザーから公開かつ未削除の栞に、フォローは正式ユーザーから登録確認済みの別ユーザーに限る。本文長、ページ番号、FK・一意制約は既存のAPI・DB仕様に従う。

### 処理の流れ

1. **生成・確定** — 初期データを作成・レビューしてJSONに固定する。LLMは初期生成時に任意で使える。通常のseedは確定済みJSONだけを読む。ユーザーは論理キー、書籍・本棚・栞・返信は固定UUID、いいね・フォローは既存の複合キーで識別する。投稿日時も固定する。
2. **接続先の確認** — 既定は既存の `db:local` で起動するPGlite（`127.0.0.1:5433`）。一般のDB接続設定から自動選択しない。開発用Supabaseは明示指定時だけ許可し、承認済み開発project refとAuth URL・DB接続先の一致を確認する。クラウドAPI経由で確認する場合は、開発Workerの認証先とHyperdriveの実接続先も確認する。クラウドへのDB接続は既存の `book_bear_api` ロールとTLS証明書検証を使う。
3. **認証の準備** — PGliteではFK検証用の代替 `auth.users` に固定UIDを用意し、同じUIDのプロフィールと表示設定を投入する。開発用Supabaseでは、開発専用アカウントを通常のAuthで事前に用意する。既存の `PUT /api/v1/me` でプロフィール・表示設定を初期化し、正式アカウントには正式JWTで登録確認を記録する。seedは専用アカウントへの論理キーとUIDの対応、Authで確認したUIDと匿名区分、プロフィールの存在・登録確認を照合してから投入する。環境別のUID対応や資格情報はGit対象外の設定で管理する。
4. **検証・投入** — JSONをZodで検証し、参照切れ、重複、SNS操作の条件を投入前に確認する。1トランザクションで、ローカル専用のAuth代替行・プロフィール・表示設定、書籍、本棚、栞、フォロー・いいね・返信の順に投入する。開発用SupabaseのAuth・プロフィール準備はこのトランザクションとは別の事前作業とする。
5. **結果確認** — データセットの版と種別ごとの追加・スキップ件数を表示する。フロントエンドの接続確認は開発用Supabaseの専用アカウントでログインし、既存APIで本棚、フィード、プロフィール、栞詳細・返信を確認する。PGliteはDB・推薦の検証に使う。UIのモックが必要な場合は固定JSONから既存OpenAPIのレスポンスに沿ったMSW用fixtureを作れるようにする。

### 再実行・例外処理

| 条件 | 動作 |
| --- | --- |
| 同じ版を再実行 | 同じキーでseed管理項目も一致する行はスキップする。日時を含め既存行を維持する。 |
| 既存行が編集済み・別データと衝突 | 内容の不一致や別キーの一意制約違反として停止する。評価にはクリーンな開発DBへ同じ版を投入する。 |
| 本番・未承認の接続先、設定不一致、Auth照合失敗、不正なJSON | 書き込み前に停止する。環境名の指定だけでは開発用と判断しない。 |
| FK違反、接続断、途中の書き込み失敗 | トランザクションをロールバックし、非0で終了する。コミット結果が不明な場合も同じキーで再実行して照合できる。失敗段階と対象の論理キーを表示し、JWT・接続文字列は出力しない。 |

## 2. 設計判断

| 採用する方針 | 比較した選択肢と理由 |
| --- | --- |
| 確定済みJSONを版管理し、生成と投入を分離 | 実行ごとのLLM生成は文章や候補が変わり、推薦結果の差を方式の違いに帰属しにくい。固定JSONなら差分をレビューでき、外部AI APIなしで再投入できる。 |
| 既存スキーマにトランザクションで投入 | 全件を既存API経由で作る方式では、サーバー採番のISBNなし書籍などのIDを固定しにくく、複数リクエストの途中失敗で一部が残る。DB投入時に業務ルールを検証し、利用時は既存APIの認可を通す。既存スキーマ・RLS・API契約を利用する。 |
| 一致する行だけスキップ | 無条件の上書きや全削除後の再投入は画面確認中の編集や共有開発データに影響する。差分を明示して止め、評価用の初期状態はクリーンな開発DBで再現する。 |
| 開発用Authは事前準備、ローカルだけ代替行 | Supabase管理の `auth.users` を直接操作する方式は認証データの整合性と権限管理を複雑にする。既存の認証フローとプロフィール初期化を使えば、画面確認にも同じアカウントを使える。 |

## 3. 検証

- 自動テストでは、固定データの整合性、2回投入後の行・日時の一致、衝突や途中失敗時のロールバック、本番・未確認の接続先やUID不一致の拒否を確認する。外部AIや実クラウドは通常のテスト・CIから分離する。
- 開発環境では、既存APIで空状態・書影なし・SNSの表示を確認し、匿名ユーザーの操作制限と第三者から非公開栞が取得できないことを確認する。評価用データの版と期待する傾向を#30に引き渡す。
