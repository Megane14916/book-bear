# 栞 CRUD（Issue #40）

- `/create` で本棚を選択。検索結果の書籍詳細からは `?bookId=`、本棚からは `?userBookId=` を渡す。
- `bookId` は書籍、`userBookId` は本人の本棚の行、`bookmarkId` は栞のID。外部候補の provider/providerId は #38 の取り込みで書籍IDに変換してから利用する。
- 本棚選択は既存の無限取得キーとページ形式を共有。後続ページの本は「本棚の続きを読み込む」で選択できる。URLの userBookId は取得済みの本人の本棚と照合する。
- 書籍から保存する場合は #39 の本棚登録処理（既存登録なら200）を再利用し、応答の userBookId で栞を作る。作成失敗後の再試行では、同じ所有者の取得済み本棚IDを再利用する。
- 閲覧では匿名認証を作らず、保存時のみ #36 の runAuthenticatedWrite に認証・PUT /me・最新JWT・認証切替時の中断を任せる。公開は正式ユーザーのみ。Google連携UIは #44 の対象。
- 保存中は同期ロックと disabled で二重送信を防ぎ、画面離脱で中断する。POST/PATCH/DELETEの自動再試行はしない。応答が失われた場合、手動のPOST再試行は別の栞を作る可能性がある（現行APIに冪等キーはない）。
- 更新後は所有者の詳細を応答カードで更新。ほかの閲覧者の詳細と一覧・フィード・プロフィール等のキャッシュは、旧本文を残さないようキャンセル後にリセットする。削除では遷移後に詳細キャッシュを除去する。書籍情報・ヘルスチェック・本棚は保持する。
- 本文は trim 後1〜2,000文字、ページは空欄nullまたは1〜2,147,483,647。総ページ数を上限にしない。編集できるのは本文・ページ・公開範囲・ネタバレだけ。
- 非公開・削除・不明IDは共通の404表示。所有者判定の最終的な強制は既存APIで行う。削除は論理削除のため、本棚削除の既存409制約は変わらない。

## 検証

`pnpm --filter web test` / `typecheck` / `build` / `check:api`。

`pnpm --filter web test:bookmarks:e2e` は既存Chromeと専用Vite（5194）を使用し、API（8797）とSupabaseのHTTPをモックする。実際のAuth SDK・APIミドルウェアを通るが、実サービスの認証・DB書き込みを検証するテストではない。認証情報の保存・trace・動画・スクリーンショット出力は無効。
